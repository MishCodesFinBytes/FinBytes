INQLabs is a generative-art studio — 40+ browser-based art generators plus an editorial gallery site. This is a technical walkthrough of how it’s built. The whole design falls out of one deliberately strict constraint, so we’ll start there and work outward to the site, the data, and the serverless backend that quietly turns a static site into a CMS.

The one constraint that shapes everything

Every generator is a single, self-contained HTML file with zero external dependencies.

No bundler, no framework, no CDN script tags. A tool is just studio/<slug>/index.html with its CSS, JavaScript, palette data, and export logic all inline. That single rule buys three things at once:

  • Portability — the same file runs as a static asset on Netlify, embeds in a Jekyll blog, or opens straight from file:// with no build step.
  • Longevity — nothing to npm install means nothing to rot. A piece made today reproduces in five years.
  • Reviewability — one file is one artefact. What you read is exactly what ships.

New tools are scaffolded from two templates that encode the house rules: _template-canvas2d.html for Canvas 2D generators (most of them) and _template-webgl.html for shader work — the fluid-simulation tools like Marbling and Reaction-Diffusion.

The loop worth noticing: publishing a piece is a git commit. A generator’s “Add to pool” button and every admin action call a serverless function that writes back to the GitHub repo; the push triggers a Netlify rebuild that serves the new content. There is no database server — git is the database.

Anatomy of a single tool

Every generated piece follows the same skeleton, enforced by the templates:

Dual-canvas signature

Two stacked canvases: #canvas draws the artwork, and a separate #sigCanvas paints the visible INQ.LAB signature. Keeping the signature on its own layer means it composites cleanly at export without the generation code ever having to know about it.

PNG metadata, injected by hand

Export doesn’t stop at canvas.toDataURL(). A small routine splices a tEXt chunk directly into the PNG byte stream, right after the IHDR, so author, copyright, and palette provenance travel inside the file:

// after the 8-byte PNG signature + 25-byte IHDR chunk,
// insert a tEXt chunk carrying "Author", "Copyright", "Palette"
function injectPNGMeta(dataURL, fmt) {
  const src = base64ToBytes(dataURL.split(',')[1]);
  const text = `Software\0INQLabs — © 2026 INQ.LAB`;   // keyword\0value
  const chunk = makeTextChunk(text);                    // len + 'tEXt' + data + CRC32
  const out = new Uint8Array(src.length + chunk.length);
  out.set(src.slice(0, 33));        // PNG sig + IHDR
  out.set(chunk, 33);               // our tEXt chunk
  out.set(src.slice(33), 33 + chunk.length);
  return bytesToDataURL(out);
}

It’s a few dozen lines of byte-wrangling (length prefix, the ASCII tEXt tag, the payload, a CRC-32), but it means provenance can’t be stripped by a right-click “Save As”.

Three non-negotiables

Every tool must ship a visible signature, embedded PNG metadata, and an on-page copyright notice. These aren’t style preferences — they’re part of the tool contract, because the output is meant to be sold and attributed.

Colour as a first-class subsystem

Palettes aren’t hard-coded per tool. Eight historical, public-domain colour sources — Sanzo Wada, Werner’s Nomenclature of Colours, Munsell, Goethe, Kalamkari, Rangoli, Warli, and natural Western dyes — ship as JSON, and every generator exposes the same palette-selector UI over a universal colour-role mapping (background / primary / accent / detail).

There’s an explicit legal stance baked in too: a documented “never use” list (Pantone, paint-manufacturer palettes, and living- or recently-deceased-artist styles). Everything is sourced from long-dead artists and cultural traditions on purpose — the provenance line in the PNG metadata is only true because the palette pipeline guarantees it.

Determinism, treated as a testable property

Because a piece is identified by its seed/state, the same seed should always reproduce the same image. That’s easy to claim and easy to break — a stray Date() baked into a constant, or an un-seeded Math.random() in a hot path, silently makes a generator non-reproducible.

So determinism is audited, per generator, in a running report that grades each tool MUST-FIX / VERIFY / clean and documents every known gap. Reproducibility here is a tested invariant, not a hope.

Export pipeline

Beyond single PNGs, the export layer handles the commercial reality of selling prints:

  • Multiple aspect ratios and print resolutions per piece.
  • Etsy and Instagram bundles — correctly-sized sets zipped client-side with JSZip (no server round-trip).
  • Sets — a “mini-series” and “split-artwork” system that renders coordinated multi-piece compositions sharing a palette and composition seeds.

The site around the tools

The generators live inside an editorial gallery site, hosted static on Netlify (publish = ".", no build command). The interesting engineering is the auth boundary.

Public vs Studio

The gallery (/, /collections/, /about/, /palettes/, /rights/, /contact/) is open. Everything under /studio/* — the generators themselves and the admin suite — is gated to an admin role. The gate is one line in _redirects:

/studio/*  /studio/:splat  200!  Role=admin
/collections/*  /collections/index.html  200

The nf_jwt cookie bridge

This is the subtle part. Netlify’s Role=admin redirect is evaluated at the edge and reads the nf_jwt cookie — but the Netlify Identity widget signs users in client-side only. Without bridging the two, the edge sees every request as anonymous and the studio 404s even when you’re “logged in.”

The fix is to mirror the Identity JWT into a cookie on every widget lifecycle event:

function syncJwt(user) {
  if (user && user.token)
    document.cookie =
      `nf_jwt=${user.token.access_token}; path=/; secure; samesite=lax`;
}

netlifyIdentity.on('init',    syncJwt);   // restore cookie on page load
netlifyIdentity.on('login',   syncJwt);   // set on sign-in
netlifyIdentity.on('refresh', syncJwt);   // Identity rotates JWTs hourly
netlifyIdentity.on('logout',  () => {      // expire immediately
  document.cookie = 'nf_jwt=; path=/; expires=Thu, 01 Jan 1970 00:00:00 GMT; secure; samesite=lax';
});

The refresh listener matters: Identity rotates the JWT every hour, so without it a long studio session would silently lose its edge authorisation.

Data architecture: YAML source, JSON runtime

Everything is a flat file in the repo, in two tiers:

TierWhereRole
Source of truth_data/*.ymlHuman-editable: collections, the piece pool, sets, the featured hero, the studio statement.
Runtimeassets/data/*.jsonMachine-fetched mirrors the pages actually read.

Collections carry a slug, status (production/wip), a featured flag (the first nine drive the homepage 3×3 grid), and a tile image. Exported pieces land in a per-collection pool (_data/pieces/<slug>.yml); sets get their own YAML with a hash, layout, and the composition seeds needed to re-render them.

The serverless “CMS”

A static site can’t mutate itself — so a set of Netlify Functions does the writing. An admin dashboard at /studio/admin/ (pool, hero, tiles, collections, statement, pieces) calls functions that commit changes straight back to GitHub through a shared helper (JWT auth + atomic commit). A weekly cron function rotates the featured hero from the pool every Sunday.

So the entire content lifecycle — generate → add to pool → promote to hero/tiles → publish — is just structured commits. No database to run, back up, or secure; the version history is the audit log.

How it’s actually built

  • Prompt-driven — the studio is built from a versioned build-prompt playbook, one prompt per tool, with deliberate asset-reuse chains (Ink Bloom’s botanical SVG library feeds the Ikebana composer; Zen Canvas feeds the Zen Generator).
  • Phased — tools first, then the auth gate, then the editorial redesign, then the pool/admin CMS, then sets and print-resolution export pipelines.
  • Python side-scripts generate the social-media reels, cards, and banners from finished pieces.
  • Local dev is python -m http.server and open localhost:8000/<tool>/ — the zero-dependency rule pays off here too.

The one-sentence version

INQLabs is a fleet of dependency-free HTML canvas/WebGL generators, standardised by two templates and a strict signature / metadata / palette contract, wrapped in a Netlify static site whose admin actions are serverless functions that commit YAML, JSON, and images back to git — a JAMstack studio where the repo is the database and publishing is a commit.
