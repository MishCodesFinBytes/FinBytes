One kitchen story, one tiny problem — every concept solved on top of it. Python is a kitchen with only one knife. Lots of cooks (threads) want to chop, but the rule is: you must hold the one knife to chop. That knife is the GIL. Only the cook holding it works; everyone else waits. Multiprocessing, asyncio and caches are all just clever ways to cook faster despite the one-knife rule.

Three cooks, one knife. Only the one holding it runs. That's the GIL.

Our one tiny problem: do a job 4 times, as fast as possible

Two flavours of job — keep both in your head, because the right tool depends on which one you have:

  • CPU job — real thinking work (big maths). The cook is busy the whole time, needs the knife nonstop.
  • I/O job — waiting work (download a page, read a file). The cook mostly stands around waiting.
# CPU job: needs the knife nonstop
def heavy(n):
    total = 0
    for i in range(2_000_000):
        total += (i * n) % 7
    return total

# I/O job: mostly just waiting
import time
def slow_io():
    time.sleep(0.2)       # waiting on the web
    return "done"

ELI10 — a CPU job is like doing hard multiplication in your head — you're working every second. An I/O job is like waiting for the kettle to boil — you're just standing there. That difference decides everything.

1 · The GIL — why only one knife?

The kitchen could have handed every cook their own knife. Instead it made one knife for the whole kitchen, because sharing safely is hard — and the thing being shared is how Python remembers to clean up (that's refcounting, next).

  • GIL = Global Interpreter Lock = the one knife. A mutex — only one holder at a time.
  • To run any Python line, a thread must hold it.
  • Python passes the knife around quickly so everyone gets turns — but never two at once.

ELI10 — one knife keeps the kitchen from descending into chaos. The downside: even with 8 cooks and 8 chopping boards, only one person actually chops at a time.

2 · Refcounting — the reason the knife exists

Every Python object keeps a little tally: how many things point at me right now? When it hits 0, nobody needs it, so Python frees the memory. That tally is the reference count.

x = []      # the list's count = 1
y = x       # same list, count = 2
del x       # count = 1
del y       # count = 0  -> memory thrown away

Adding 1 to the tally is secretly three steps: read the number, add one, write it back. If two cooks do this at the same instant, they clobber each other:

A too-low count frees a bowl still in use (crash); too-high never frees it (leak). That mess is a race condition.

Two ways to prevent it: (1) give every object its own tiny lock — millions of locks, slow and fiddly; or (2) put one big lock around the whole kitchen so two cooks can never touch a tally at the same moment. Python picked #2. That one big lock IS the GIL.

ELI10 — rather than give every toy its own guard, Python hires one guard for the whole room. Simple and cheap — but only one kid can play at a time.

3 · Threads — many cooks, one knife

Threads are extra cooks in the same kitchen. Because of the one knife they can't chop simultaneously, so:

  • CPU job → threads don't help. Everyone wants the knife nonstop; they just queue.
  • I/O job → threads DO help. A waiting cook hands the knife over while the kettle boils, so another thread grabs it and works.
# I/O work: 4 jobs at once, threads share the free knife during waits
import threading
ts = [threading.Thread(target=slow_io) for _ in range(4)]
[t.start() for t in ts]; [t.join() for t in ts]
# measured: 0.8s sequential  ->  0.2s with threads  (4x faster)

ELI10 — four kettles boiling at once beats boiling them one after another — even with a single cook — because waiting is free.

4 · Multiprocessing — CPU job? Build more kitchens

One knife per kitchen, so for real CPU work don't add cooks — add whole kitchens. Each process is its own separate Python with its own knife (its own GIL). Four kitchens on a four-core machine chop at the same time for real: true parallelism.

# CPU work: give each job its own kitchen (its own GIL)
import multiprocessing
with multiprocessing.Pool(4) as pool:
    pool.map(heavy, range(4))
# measured: threads gave NO speedup; processes were genuinely faster

The catch: separate kitchens don't share a fridge. Threads share memory for free; processes are isolated, so sending data between them means copying it (pickle → send → unpickle) through a queue or shared-memory block. More RAM, slower hand-offs. You trade easy sharing for real parallelism.

ELI10 — two separate kitchens cook twice as fast, but passing a bowl between them means walking it next door, not just reaching over.

5 · asyncio — one super-organised cook who never stands idle

asyncio is the odd one out — it's not about the GIL at all. One cook, one kitchen, one knife, zero parallelism. Its trick is simply never wasting a waiting moment. The cook works until they hit an await ("I've started the kettle"), then says "go do something else" and the event loop starts the next job. It's cooperative: each job politely steps aside at await points.

# thousands of I/O jobs, single thread, cooperative
import asyncio
async def slow_io_async():
    await asyncio.sleep(0.2)          # the "start the kettle" moment

async def main():
    await asyncio.gather(*[slow_io_async() for _ in range(4)])
asyncio.run(main())
# measured: 0.2s for all 4 — same win as threads, far lighter

ELI10 — a great short-order cook starts the toast, cracks eggs while it toasts, flips bacon while the eggs cook — one person, never idle. Nothing happens at the same time; no second is wasted.

6 · Caches — don't do the same work twice

Totally different axis. Concurrency = doing many things at once. A cache = remembering an answer so you never redo it. In the kitchen: write the recipe result on a sticky note; next time someone asks, read the note instead of cooking again. Python's built-in is functools.lru_cache, which memoizes a function's output for each set of inputs:

from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)

fib(35)   # without cache: millions of repeats. With cache: instant.

Why "LRU"? Least Recently Used. maxsize=128 keeps only the 128 most-recent answers; when full it throws out the one unused longest. That "which one do we throw out?" rule is an eviction policy, and there are several:

PolicyELI10Where you meet it
LRU — Least Recently UsedToss the note you haven't looked at in longest.lru_cache, browsers
LFU — Least Frequently UsedToss the note you've used fewest times.CDNs, DB caches
FIFO — First In First OutToss the oldest note, no matter what.simple queues
TTL — Time To LiveNotes expire after N seconds (stay fresh).web/API caches, DNS

Other kinds of cache you'll hear about:

  • In-memory (like lru_cache): fastest, but forgotten when the program stops.
  • Disk cache: saved to a file, survives restarts, slower.
  • Distributed cache (Redis / Memcached): one shared note-board many computers read from.
  • CPU cache (L1/L2/L3): tiny ultra-fast memory inside the chip — the same idea, in hardware.

Two rules for lru_cache: inputs must be hashable (they're the note's label), and the function should be pure — same input always gives the same output. Caching something that depends on the time, randomness, or a database gives stale, wrong answers.

ELI10 — if Grandma always asks the same maths question, write the answer on a sticky note once. Just don't cache "what time is it?" — that note goes stale instantly.

One example the whole way down: a crawler pipeline that fetches URLs and scores the HTML. Each concept is motivated by the previous one — a single causal chain from why the GIL exists to when you route around it.

The running example — a two-stage crawler pipeline

Two stages, sitting on opposite ends of the spectrum. That contrast drives every decision that follows.

import time, hashlib

URLS = [f"https://example.com/page/{i}" for i in range(8)]

def fetch(url):        # STAGE 1 — I/O-bound: mostly blocked on a socket
    time.sleep(0.1)    # stand-in for the network round trip
    return f"<html>{url} " + ("word " * 5000) + "</html>"

def score(html):       # STAGE 2 — CPU-bound: 200 SHA-256 rounds, never blocks
    h = html.encode()
    for _ in range(200):
        h = hashlib.sha256(h).digest()
    return sum(h)

fetch spends ~99% of its wall-clock time blocked in a syscall waiting for bytes. score spends 100% of its time executing on a core. That distinction is the single fact that determines which concurrency primitive is correct.

baseline  sequential: [score(fetch(u)) for u in URLS] → 0.80 s

STEP 1 · THE ROOT CAUSE

Reference counting, and why it isn't thread-safe

Every PyObject begins with a header containing ob_refcnt. When fetch returns an HTML string and you bind it, CPython adjusts that field via the C macros Py_INCREF / Py_DECREF. When it reaches zero, score's intermediate bytes objects are deallocated immediately — deterministic, not "someday" like a tracing GC.

import sys
html = fetch(URLS[0])
sys.getrefcount(html)   # -> 2  (your name + the temporary arg to getrefcount)
alias = html
sys.getrefcount(html)   # -> 3

Now imagine two threads both drop their reference to the same html page at once. Py_DECREF is, at the C level, roughly ob_refcnt = ob_refcnt - 1; if (ob_refcnt == 0) dealloc() — a read-modify-write, not atomic. Interleave two of them:

Fixing this per-object — a lock or atomic on every refcount touch — would put an atomic op on the hottest path in the interpreter (refcounts churn on virtually every bytecode). That was measured as prohibitively slow for the common single-threaded case.

→ leads to: instead of millions of fine-grained locks, CPython takes one coarse lock around the whole interpreter. That lock is the GIL.

STEP 2 · THE MECHANISM

What the GIL actually is, and when it's released

The GIL is a single mutex (today a condition-variable-backed struct in ceval.c) that a thread must hold to execute bytecode in the CPython eval loop. Consequences that fall straight out of that:

  • Individual bytecodes and refcount updates are effectively serialized — no two threads mutate ob_refcnt concurrently, so Step 1's race can't happen.
  • A running thread doesn't hold the GIL forever. The eval loop checks a request flag on a cadence set by sys.setswitchinterval() — default 5 ms — and drops the GIL so another thread can run.
  • Crucially, the GIL is explicitly released around blocking C calls. time.sleep, socket reads, and file I/O wrap the blocking call in Py_BEGIN_ALLOW_THREADS … Py_END_ALLOW_THREADS. So during fetch's wait, the GIL is free.
import sys
sys.getswitchinterval()   # -> 0.005   (5 ms time-slice for CPU-bound threads)

→ splits the problem in two: fetch hands the GIL back while blocked (so threads help), score never does (so threads are useless for it). The next three steps follow directly.

STEP 3 · CONSEQUENCE FOR I/O

Threads — overlap the fetch waits

Because fetch releases the GIL inside the blocking read, N threads' waits overlap. While thread A is parked in the syscall, thread B holds the GIL and issues its own request. You get near-linear speedup on Stage 1 despite only one thread ever running Python bytecode at a time.

from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor(8) as tp:
    pages = list(tp.map(fetch, URLS))   # 8 waits overlap → ~0.1s not 0.8s

But push the same pool at score and you get nothing: every thread wants the GIL continuously, so they round-robin on the 5 ms interval and finish no faster than sequential — plus a little context-switch overhead. This is the classic "threading didn't speed up my CPU code" result, working exactly as designed.

→ but: Stage 2 (score) is still the bottleneck and threads can't touch it. To parallelize CPU work you must escape the single GIL entirely.

STEP 4 · CONSEQUENCE FOR CPU

Multiprocessing — N interpreters, N GILs

Fork/spawn separate processes; each has its own interpreter, its own memory, and its own GIL. Now score runs truly in parallel across cores. The cost is the process boundary: arguments and return values cross it by pickling (serialize → pipe → unserialize), and each worker is a full interpreter (memory + startup cost).

from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(4) as pp:
    scores = list(pp.map(score, pages))   # real parallelism across 4 cores

Two practical corollaries of "separate memory": objects aren't shared (mutating a global in a worker doesn't affect the parent), and passing large payloads is expensive because they're copied through the pickle pipe. For big shared arrays you reach for multiprocessing.shared_memory to skip the copy.

→ combine 3 + 4: the pipeline wants threads for the I/O stage and processes for the CPU stage. concurrent.futures gives both the same Executor.map API, so you compose them.

# fetch on threads (I/O), then score on processes (CPU)
with ThreadPoolExecutor(8) as tp:
    pages = list(tp.map(fetch, URLS))
with ProcessPoolExecutor(4) as pp:
    scores = list(pp.map(score, pages))
measured  sequential 0.80 s  →  threads+processes 0.14 s

STEP 5 · A DIFFERENT ANSWER FOR I/O

asyncio — one thread, thousands of in-flight fetches

Threads solve the I/O stage but cost an OS thread and ~5 ms-sliced scheduling per unit. When you need thousands of concurrent fetches, that overhead dominates. asyncio replaces OS-thread concurrency with a single-threaded event loop over non-blocking sockets (via epoll/kqueue selectors).

The mechanics link straight back to Step 2's "released while blocked": instead of the C layer releasing a lock during a blocking syscall, the coroutine suspends itself at await and hands control to the loop, which registers the socket with the selector and resumes the coroutine when data is ready. No GIL contention because there's only one thread; concurrency is cooperative, not preemptive.

import asyncio, aiohttp

async def fetch(session, url):
    async with session.get(url) as r:
        return await r.text()          # suspend here; loop runs other fetches

async def main():
    async with aiohttp.ClientSession() as s:
        return await asyncio.gather(*[fetch(s, u) for u in URLS])

Two hazards, both consequences of "single thread, cooperative": (1) a score-style CPU loop inside a coroutine blocks the entire loop — nothing else progresses until it yields; (2) a synchronous requests.get call has no await, so it also stalls everything. The bridge back to Steps 3–4 is run_in_executor, which offloads blocking/CPU work to a thread or process pool:

loop = asyncio.get_running_loop()
# push the CPU stage onto processes without blocking the loop
result = await loop.run_in_executor(process_pool, score, html)

→ orthogonal optimization: all of Steps 3–5 are about doing many things concurrently. None of them help if you keep recomputing the same result. That's caching.

STEP 6 · A DIFFERENT AXIS ENTIRELY

Caching — eliminate the work instead of parallelizing it

Concurrency divides the work across time/cores. A cache removes repeated work. If the crawler sees the same page twice, score is a pure function of its input — same HTML, same result — so it's a textbook memoization target.

from functools import lru_cache

@lru_cache(maxsize=256)
def score(html):        # must be hashable args + deterministic output
    ...

# after processing 8 unique pages twice:
score.cache_info()      # CacheInfo(hits=8, misses=8, maxsize=256, currsize=8)

Mechanically, lru_cache is a dict keyed by the (hashable) arguments, plus a doubly-linked recency list. On a hit it returns the stored value in O(1); on a miss it computes, stores, and — if currsize == maxsize — evicts the least-recently-used entry. That policy is one choice among several, each mapping to a real system:

PolicyEvictsCost / structureSeen in
LRUleast-recently-useddict + recency list, O(1)functools.lru_cache
LFUleast-frequently-usedneeds frequency countsCDN edge caches
FIFOoldest insertedplain queuesimple ring buffers
TTLentries past an expirytimestamp per entryDNS, HTTP Cache-Control

Where the cache physically lives

  • In-process (lru_cache, functools.cache): a Python dict on the heap. Fastest, but not shared across the Step-4 processes — each worker has its own, and it dies with the process.
  • On disk (shelve, diskcache): survives restarts, slower, serialized.
  • Distributed (Redis / Memcached): one store many workers/machines share — the right answer once you've split into processes and want a shared cache with TTL eviction.
  • Hardware (CPU L1/L2/L3): the same locality principle in silicon; the score hash loop is fast partly because its working set fits in L1.

Correctness caveats are just the definition of memoization enforced: keys must be hashable (they index the dict) and the function must be pure. Caching fetch directly would be wrong unless you add a TTL — the page can change under you, so you'd want Cache-Control/ETag semantics rather than an unbounded lru_cache.

Deeper cuts

  • GIL scheduling internals: pre-3.2 used an opcode-count check (bad for latency); 3.2+ uses the time-based gil_drop_request flag with the setswitchinterval cadence. There's still a known "convoy effect" where a CPU thread starves an I/O thread that keeps re-acquiring.
  • Free-threaded CPython (PEP 703): 3.13 ships an experimental --disable-gil build. To keep refcounting safe without the GIL it uses biased reference counting, per-object locks, and immortal objects for common singletons. This is the real path to removing the lock this whole document is about.
  • Sub-interpreters (PEP 684 / 734): 3.12+ gives each interpreter its own GIL within one process — a middle ground between threads and multiprocessing, with an interpreters module in 3.13+.
  • The GIL is a CPython detail: Jython (JVM) and IronPython (.NET) never had one; PyPy has one but with different release behaviour.
  • C extensions opt out: NumPy, hashlib, zlib and friends drop the GIL around long C computations, which is why some "CPU" work in Python is already parallel across threads.

Timings measured on one machine: sequential 0.80 s → threads+processes 0.14 s → cached second pass 0.003 s (8 hits / 8 misses).

Nice-to-know extras (bonus points in interviews)

  • concurrent.futures — one tidy interface for both: ThreadPoolExecutor (I/O) and ProcessPoolExecutor (CPU). Swap one word to switch strategies.
  • Mixing async + blocking code: never call a slow blocking function straight inside a coroutine (it freezes the whole loop). Use loop.run_in_executor() to shove it onto a thread.
  • Locks aren't gone: the GIL protects Python's internals, not your logic. Your own shared counters still need threading.Lock.
  • The GIL is being removed: Python 3.13 shipped an experimental free-threaded ("no-GIL") build — PEP 703. The first real path to true multi-thread parallelism in CPython.
  • Only CPython has it: the GIL is an implementation detail. Jython and IronPython never had one.

Say-it-out-loud interview lines

What's the GIL? — "A lock in CPython that lets only one thread run Python code at a time. It exists because reference counting isn't thread-safe, and one lock is simpler than locking every object."

Why does it matter? — "Threads don't give real parallelism for CPU work — they take turns. For CPU work I use multiprocessing; for I/O, threads or asyncio, because the GIL is released while waiting."

asyncio vs threads? — "asyncio is single-threaded cooperative concurrency — best for thousands of I/O tasks. Threads are simpler for a handful."

And caching? — "Different problem — not doing the same work twice. lru_cache memoizes pure functions; LRU evicts the least-recently-used entry when full."
