A Python variable is a name bound to an object, not a box that holds a value. Every value — an int, a list, a function — is a PyObject on the heap; a variable is just a reference (a pointer) to one. Assignment never copies the object, it binds a name to the same object.

a = [1, 2, 3]
b = a            # both names reference the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]  — one object, two names

So value and identity are separate questions: == compares contents, is compares object identity (id(x) is essentially its address). Python tracks how many references point at each object — its reference count — and frees the object the moment that count hits 0.

x = [1, 2]; y = [1, 2]
x == y   # True  — same contents
x is y   # False — two distinct objects

Mutable vs immutable

The dividing line is whether an object's value can change after it is created.

Change in place?Built-in types
ImmutableNo — operations produce a new objectint, float, bool, complex, str, bytes, tuple, frozenset, None
MutableYes — edited in placelist, dict, set, bytearray, most class instances

With an immutable object, an operation that looks like a change actually rebinds the name to a new object and leaves the original untouched. With a mutable one, the same object is modified — so every name pointing at it sees the change:

x = 5
y = x
x += 1        # int is immutable: a NEW 6 is created, x is rebound; the 5 is unchanged
print(x, y)   # 6 5

a = [1, 2]
b = a
a += [3]      # list is mutable: the SAME list is extended in place
print(a, b)   # [1, 2, 3] [1, 2, 3]   — b sees it too

Why the language is built this way

  • Hashability → dict keys and set members. A hash must stay constant for the object's whole life. Immutable objects can guarantee that, so they're hashable; mutable ones generally aren't (a list or dict can't be a key). A tuple is hashable only if everything inside it is.
  • Safe sharing. An object that can never change can be shared freely — across functions, or across threads — with no risk of one holder mutating it under another. Immutable objects are inherently thread-safe.
  • Interning / caching. Because they never change, CPython safely reuses a single copy of common immutables — the ints -5…256 and interned short strings — to save memory. This is only sound because they're immutable.
  • Predictable copy semantics. Assignment only ever aliases (points a new name at the same object). When you genuinely need an independent mutable copy, you ask for one: list(x), x.copy(), or copy.deepcopy(x) for nested structures.

Classic foot-guns that fall straight out of this model:

  • Mutable default arguments. def f(x, acc=[]) creates the list once, at definition time; every call without acc shares and mutates the same one. Use acc=None and acc = acc if acc is not None else [] inside.
  • Aliasing. b = a on a list means edits through either name show through both — copy if you want independence.
  • is vs ==. Interning makes 256 is 256 True but 257 is 257 possibly False — never use is to compare values; reserve it for None / True / False and genuine identity checks.

The same reference-counting foundation is why concurrency needs care — see the concurrency note and the GIL note.

Where does a variable keep its value?

In some languages a variable is a box you drop a value into. In Python it's more like a sticky name-tag you stick onto a thing. The actual value sits on a big shared table (the computer's memory), and the name is just a label pointing at it. You can even stick two name-tags on the same thing.

a = [1, 2, 3]
b = a          # you stuck a second tag, b, on the SAME list
b.append(4)
print(a)       # [1, 2, 3, 4] — one thing, two name-tags

Why do it this way instead of copying? Because copying everything on every = would be slow and waste memory. Pointing a new label at the same thing is instant. To know when a thing is safe to throw away, each thing keeps a little tally of how many name-tags are stuck on it — when the last tag comes off, it gets binned. (That tally is the "reference count.")

Mutable vs immutable: can you change the thing itself?

Some things you can change; some you can't — that's the whole idea.

  • Mutable = a whiteboard. You can rub bits out and add new bits without getting a new board. list, dict, set work like this. If two name-tags are on the same list and you change it, both tags see the change.
  • Immutable = a printed photo. Once it's made you can't edit it — if you want it different you have to print a new one. int, str, tuple, bool work like this.

This trips people up with numbers. It looks like you're changing one, but you're not:

x = 5
y = x        # y points at the same 5
x = x + 1    # but 5 can't change! Python makes a NEW 6 and moves x's tag to it
print(x, y)  # 6 5  — y is still on the old 5

Compare that to a list, which really does change in place:

a = [1, 2]
b = a
a.append(3)   # the list itself is edited
print(b)      # [1, 2, 3] — b sees it, because it's the same thing

Why make some things un-changeable on purpose?

  • It's safe. If a thing can never change, you can hand it to anyone and nobody can mess it up behind your back. That's gold when lots of workers (threads) share it — no nasty surprises.
  • It can be shared and reused. Because they never change, Python quietly reuses the same little numbers and short words everywhere instead of making copies.
  • It can label a drawer. Only immutable things can be dictionary keys or go in a set — the filing system needs a key that won't change out from under it. A list can't be a key; a tuple can.
The trick to remember: a variable is a name-tag on a thing, not a box. Mutable things (list/dict/set) you can edit in place, so two names can surprise each other. Immutable things (int/str/tuple) can't be edited — Python makes a new one and moves your tag. Un-changeable things are safe to share, which is exactly why they're friendly to threads.
