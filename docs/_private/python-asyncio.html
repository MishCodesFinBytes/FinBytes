How Python stores data in a variable

A Python variable is not a box that holds a value — it is a name bound to an object. Every value (an int, a list, a function) is a PyObject living on the heap, and a variable is just a reference (a pointer) to one. Assignment never copies the object; it binds a name to the same object.

a = [1, 2, 3]
b = a            # b is NOT a copy — both names point to the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]  — one object, two names

Two names, one object — so when threads share memory, they're sharing the very same objects.

That's why value and identity are different questions. == asks "do these objects contain the same value?"; is asks "are these the same object in memory?" (id(x) is essentially its address).

x = [1, 2]; y = [1, 2]
x == y     # True  — same contents
x is y     # False — two distinct objects
z = x
z is x     # True  — same object, two names

Reference counting. Each object carries a small integer — its ob_refcnt — counting how many references point at it right now. Binding a name, appending to a container, or passing an argument bumps it up; rebinding, del, or a name going out of scope bumps it down. When the count hits 0, nothing can reach the object, so CPython frees it immediately — deterministic cleanup, unlike a tracing garbage collector. (A separate cyclic collector mops up reference cycles that never reach 0.)

import sys
a = []
sys.getrefcount(a)   # 2 — the name 'a' + the temporary argument to getrefcount
b = a
sys.getrefcount(a)   # 3 — 'b' references the same object too
del b
sys.getrefcount(a)   # 2 again

Small immutables are shared to save memory: CPython caches the ints -5…256 and interns short strings, so 256 is 256 is True but 257 is 257 may be False. Never use is to compare values — only for identity and for the singletons None / True / False.

What "multithreading" means in Python

Threads inside one process share the same memory — the same object graph. That's what makes threads cheap (nothing is copied), but also dangerous: if two threads touch the same object at once they can corrupt it. And they touch shared state constantly, because the ob_refcnt above is mutated on almost every operation — every name binding, every argument pass. Changing a refcount is really read → add → write, which is not atomic; two threads doing it at the same instant would clobber each other and either leak the object or free it while it's still in use (a crash).

CPython's answer is the GIL (Global Interpreter Lock): one lock a thread must hold to execute any Python bytecode, so only one thread runs Python at a time. One coarse lock is simpler and faster for the common single-threaded case than putting a lock on every object. That single fact shapes everything below:

  • CPU-bound work → threads don't help. Two threads doing heavy maths just take turns on the one GIL — no speedup. Use multiprocessing: separate processes, each with its own interpreter and its own GIL, for real parallelism.
  • I/O-bound work → threads help. The GIL is released while a thread blocks on a socket, a file, or time.sleep(), so another thread runs during the wait. asyncio gets the same overlap on a single thread, cooperatively.

One escape hatch: immutable objects — int, str, tuple and friends — can't be changed at all, so no thread can corrupt one mid-use; they're safe to share without a lock. That's the mutable-vs-immutable split from the data-types note:

Immutable objects can't change, so sharing them across threads is always safe; mutable objects are the ones that need a lock.

So "multithreading in Python" gives you real OS threads and genuine concurrency for waiting, but not parallel execution of Python code. (Full detail in the GIL note; the experimental free-threaded 3.13+ build is starting to change this.)

asyncio — cooperative concurrency on one thread

asyncio runs on a single-threaded event loop. The loop maintains a queue of tasks — scheduled coroutines. On each iteration it picks a ready task, runs it until it hits an await, then suspends it and moves to the next ready task. There is no thread switching and no parallelism; concurrency comes from coroutines voluntarily yielding control.

A coroutine is a function defined with async def. Calling it does not execute it — it returns a coroutine object. To run it you either await it from another coroutine, or wrap it in a task with asyncio.create_task(), which schedules it on the event loop and lets it run concurrently with the caller. await suspends the current coroutine and hands control back to the event loop until the awaited thing completes.

The critical pitfall is blocking the event loop. Any call that does not release control — time.sleep(), synchronous file I/O, a requests.get(), a CPU-heavy loop — freezes every other coroutine for its entire duration. The event loop is cooperative; it cannot preempt you. Use asyncio.sleep() in place of time.sleep(), and loop.run_in_executor() to push genuinely blocking work into a thread pool.

import asyncio

async def fetch(n):
    print(f"start {n}")
    await asyncio.sleep(1)   # yields control — other tasks run here
    print(f"done {n}")
    return n

async def main():
    # gather runs all three concurrently; total wall time ~1s, not 3s
    results = await asyncio.gather(fetch(1), fetch(2), fetch(3))
    print(results)   # [1, 2, 3]

asyncio.run(main())

Watch out: asyncio.gather() runs coroutines concurrently within the event loop, but they still execute one at a time — if any coroutine contains a blocking call with no await, it starves the others for the entire duration of that call.

threading — concurrent I/O with real threads

threading.Thread runs a Python function in a separate OS thread. Unlike asyncio, thread switching is handled by the OS and the GIL — you don't write await. Create a thread with target and optional args, call start() to launch it, and join() to block until it finishes.

Daemon threads. A thread created with daemon=True is killed automatically when the main thread exits — you don't wait for it. Use this for background housekeeping (heartbeat pings, log flushers, cache warmers) where it is acceptable for the work to be cut short. Non-daemon threads keep the process alive until they finish.

The GIL is released during I/O waits, so threading delivers real concurrency for network-bound or file-bound work. For CPU-bound work it provides no speedup — threads still take turns on the GIL. Use ThreadPoolExecutor from concurrent.futures for a higher-level API that handles pool sizing and result collection.

import threading
import time
from concurrent.futures import ThreadPoolExecutor

def fetch(n):
    print(f"start {n}")
    time.sleep(1)          # simulates I/O — GIL released here
    print(f"done {n}")
    return n

# Manual threads
threads = [threading.Thread(target=fetch, args=(i,)) for i in range(3)]
for t in threads:
    t.start()
for t in threads:
    t.join()               # wait for all to finish; ~1s wall time, not 3s

# Daemon thread — lives in the background, dies when main thread exits
def heartbeat():
    while True:
        print("ping")
        time.sleep(5)

t = threading.Thread(target=heartbeat, daemon=True)
t.start()                  # no join needed; killed automatically on exit

# ThreadPoolExecutor — same concurrency, higher-level API
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(fetch, range(4)))

Watch out: join() without a timeout will block forever if a thread hangs. Pass timeout= seconds and check t.is_alive() afterwards to detect stalls.

Synchronisation — Lock, RLock, Semaphore

When multiple threads share mutable state, you get race conditions: two threads read-modify-write the same value and one overwrites the other's result. Synchronisation primitives coordinate access.

Lock — a mutex: only one thread holds it at a time. Always use the context manager (with lock:) so the lock is released even if an exception is raised. A thread that calls lock.acquire() while another holds it blocks until the lock is released.

RLock (reentrant lock) — like Lock but the same thread can acquire it multiple times without deadlocking. Useful when a locked method calls another method that acquires the same lock on the same object.

Semaphore — allows up to N threads through simultaneously. The canonical use is rate-limiting: cap concurrent API calls or database connections to avoid overwhelming a downstream resource.

Deadlock — thread A holds lock 1 and waits for lock 2; thread B holds lock 2 and waits for lock 1. Neither can proceed. Prevention: always acquire multiple locks in the same order across all threads, or use lock.acquire(timeout=5) and back off on failure.

import threading
import time

# Lock — fix a race condition on a shared counter
counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(100_000):
        with lock:           # only one thread inside at a time
            counter += 1     # safe — no lost updates

threads = [threading.Thread(target=increment) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)               # always 500_000

# Semaphore — limit to 3 concurrent API calls
sem = threading.Semaphore(3)

def call_api(n):
    with sem:                # blocks if 3 threads are already inside
        print(f"calling {n}")
        time.sleep(0.5)

threads = [threading.Thread(target=call_api, args=(i,)) for i in range(10)]
for t in threads: t.start()
for t in threads: t.join()

Watch out: acquiring two locks in different orders in different code paths will eventually deadlock. If you need multiple locks, always acquire them in the same fixed order everywhere.

multiprocessing — true parallelism for CPU-bound work

Each multiprocessing.Process is a separate OS process with its own Python interpreter and its own GIL. There is no shared GIL — processes run truly in parallel across CPU cores. Use multiprocessing for CPU-bound work (number crunching, image processing, data transformation) where threads would be serialised by the GIL.

Pool.map(fn, iterable) distributes work across a pool of worker processes and returns results in input order. ProcessPoolExecutor from concurrent.futures is the equivalent higher-level API.

For inter-process communication, use multiprocessing.Queue (safe for multiple producers and consumers) or Pipe (two-endpoint channel for one producer / one consumer). Data crossing process boundaries must be picklable — lambdas, closures, and open file handles cannot be pickled.

The costs: each process copies the parent's memory space at startup (fork on Linux/macOS, spawn on Windows), startup is slower than a thread, and passing large objects between processes carries serialisation overhead. For small tasks the overhead exceeds any gain from parallelism.

import multiprocessing
import time
from concurrent.futures import ProcessPoolExecutor

def crunch(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":   # required on Windows — guards the spawn entry point

    numbers = [10_000_000] * 8

    # Sequential — one core
    start = time.time()
    results = [crunch(n) for n in numbers]
    print(f"sequential: {time.time() - start:.2f}s")

    # Pool — distribute across all cores, truly parallel
    start = time.time()
    with multiprocessing.Pool() as pool:
        results = pool.map(crunch, numbers)
    print(f"pool: {time.time() - start:.2f}s")   # ~8x faster on 8 cores

    # ProcessPoolExecutor — same result, futures API
    with ProcessPoolExecutor() as exe:
        results = list(exe.map(crunch, numbers))

Watch out: always guard multiprocessing entry points with if __name__ == "__main__":. On Windows, each worker imports the module from scratch — without the guard, spawning workers triggers infinite recursive spawning.

Imagine one waiter serving many tables. The waiter doesn't clone themselves — they take an order, go put it in, then immediately serve another table while the kitchen works. They're always moving; they never stand waiting. That's asyncio: one thread, many tasks, switching whenever a task is waiting for something.

The key rule is that tasks have to choose to hand control back — they're not interrupted. An await is the waiter saying "I'm done with this table for now, let me go do something else." A task that never awaits freezes every other task for its entire duration, because nobody else gets a turn.

import asyncio

async def fetch(n):
    print(f"start {n}")
    await asyncio.sleep(1)   # hands control back — other tasks run here
    print(f"done {n}")

async def main():
    await asyncio.gather(fetch(1), fetch(2), fetch(3))
    # start 1, start 2, start 3 ... then done 1, done 2, done 3
    # total ~1s, not 3s

asyncio.run(main())
The trick to remember: if a function doesn't await anything, it blocks the whole event loop — use asyncio.sleep(0) to yield briefly, or push blocking work to a thread pool with run_in_executor.

Threading is like hiring multiple waiters. Each one can serve different tables at the same time — but there's only one order pad (the GIL), so they still have to take turns writing. When a waiter is just waiting for the kitchen they put the pad down, so someone else can grab it. That's why threading helps for I/O-bound work (lots of waiting) but not CPU-bound work (everyone needs the pad constantly).

A daemon thread is like the person whose job is to refill the napkin dispensers. They keep going in the background as long as the restaurant is open. When the restaurant closes for the night, they stop — you don't wait for them to finish their current round.

import threading, time

def fetch(n):
    time.sleep(1)    # waiting on the kitchen — pad is free for other waiters
    return n

threads = [threading.Thread(target=fetch, args=(i,)) for i in range(3)]
for t in threads: t.start()
for t in threads: t.join()   # ~1s wall time, not 3s

Locks and Semaphores are about sharing one scarce resource safely.

A Lock is a single pen. Only one waiter can hold it at a time. If two waiters tried to write on the same ticket simultaneously, the order would be gibberish — so they queue for the pen, write, and pass it on.

A Semaphore is a box with N pens. Up to N waiters can write at once; the rest wait for a pen to be returned. Use it when you want to cap how many threads do something simultaneously — e.g. at most 3 waiters can place orders with the kitchen at once so they don't get overwhelmed.

import threading

lock = threading.Lock()
counter = 0

def safe_increment():
    global counter
    with lock:       # grab the pen — nobody else can be here
        counter += 1 # write — pen goes back automatically on exit

Multiprocessing is opening multiple separate restaurants. Each has its own staff, its own kitchen, its own pen. Truly parallel — no sharing, no GIL, no queuing. Perfect when you need eight dishes cooked at the same time and each one maxes out a chef for the entire cooking time.

The downside: if restaurant A needs to send food to restaurant B, it can't just hand a plate across — it has to bag it up, call a courier (the Queue or Pipe), and unpack it at the other end. For small jobs the courier overhead costs more than just cooking it in one restaurant.

import multiprocessing

def crunch(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":
    with multiprocessing.Pool() as pool:
        results = pool.map(crunch, [10_000_000] * 8)
        # 8 chefs cooking 8 dishes simultaneously — ~8x faster
When to use which: asyncio for many concurrent I/O tasks in one thread — threading for simpler I/O-bound scripts that benefit from real threads — multiprocessing when you need multiple CPU cores working in parallel.

The whole topic as one story — each step exists because of the one before it.

1 · A variable is a name, not a box

Every value in Python is an object on the heap. A variable is just a name pointing at one, and assignment shares the object rather than copying it (b = a gives two names for one list). Hence two different questions: == (same value?) versus is (same object?).

2 · Objects count their own references

Each object holds a reference count. Every name binding or argument pass bumps it up; every del or scope-exit bumps it down. At 0 the object is freed immediately — simple, fast, deterministic.

3 · Threads share the object graph — which breaks refcounting

Threads in one process see the same objects. But the refcount is touched on nearly every operation, and bumping it is a non-atomic read → add → write. Two threads at once corrupt it → freed-too-early crashes or never-freed leaks. A race condition at the very core of the interpreter.

4 · The GIL is the fix — and the catch

CPython wraps the interpreter in one lock, the GIL: only one thread runs Python bytecode at a time. That makes refcounting safe cheaply — but it means threads never execute Python in parallel.

5 · So the tool depends on the problem

  • CPU-bound (maths, crunching) → multiprocessing: separate processes, each with its own GIL → real parallelism.
  • Lots of I/O (network, files) → asyncio: one thread, cooperative, control freed during every wait → thousands of tasks cheaply.
  • A bit of I/O → threading: real threads, GIL released while blocked, simpler than asyncio.

6 · Each tool brings its own problem

  • asyncio — one blocking call with no await freezes every task; never block the loop (offload with run_in_executor).
  • threading — the GIL protects the interpreter, not your logic, so your own shared state still races; you need Lock, and over-locking risks deadlock.
  • multiprocessing — no shared memory; data crosses the process boundary by pickling (copy + overhead).
The whole arc in one line: variables share objects → objects count references → threads racing on those counts forced the GIL → the GIL kills thread parallelism → so use multiprocessing for CPU and asyncio/threads for I/O, each with its own failure mode.

The 30-second story

Variables are names bound to heap objects; each object reference-counts itself. Threads share those objects, but refcount updates aren't atomic, so CPython added the GIL — one thread runs Python at a time. Consequence: threads don't parallelise CPU work. Use multiprocessing for CPU, asyncio/threads for I/O (the GIL is released while waiting).

One-liners

  • GIL — a mutex letting only one thread run Python bytecode at a time; exists because reference counting isn't thread-safe.
  • Coroutine — an async def function that suspends at await and yields to the event loop; not a thread.
  • Thread vs process — threads share memory + the GIL (concurrent, not parallel for Python); processes have separate memory + their own GIL (truly parallel).
  • Race condition — two threads mutating shared state at once; result depends on timing.
  • Deadlock — two threads each holding a lock the other needs; both wait forever.
  • Daemon thread — background thread killed automatically when the main thread exits.
  • == vs is — value equality vs same-object identity.

Gotchas they probe

  • Threads give no speedup for CPU-bound Python — the GIL. (Classic trap.)
  • A blocking call inside a coroutine freezes the whole event loop.
  • The GIL protects the interpreter, not your data — you still need Lock.
  • if __name__ == "__main__": guard is required for multiprocessing (spawn re-imports the module).
  • Don't use is to compare values — interning makes it look right, then it breaks.
  • Free-threaded (no-GIL) builds arrived experimentally in 3.13 (PEP 703).

Say it out loud

"Why doesn't threading speed up my CPU code?" — "The GIL lets only one thread run Python at a time, so CPU-bound threads just take turns. I'd use multiprocessing for real parallelism."

"asyncio vs threads?" — "asyncio is single-threaded cooperative concurrency, best for thousands of I/O tasks; threads are real OS threads, simpler for a handful. Neither parallelises CPU work."

"Why does the GIL exist at all?" — "Reference counting isn't thread-safe; one interpreter-wide lock is cheaper than locking every object."
